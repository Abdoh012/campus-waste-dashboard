# Frontend architecture

React 19 + Vite 8 + TypeScript single-page app. It runs entirely on local mock
data — there is no backend.

## Layers

```
src/
├─ main.tsx                  Entry point: mounts <App>.
├─ App.tsx                   Application shell. Owns only the state both screens
│                            share (the presentational sign-in gate), mounts the
│                            single notification stack, then renders the active
│                            page.
├─ pages/                    One component per screen: LoginPage and
│                            DashboardPage. A page composes feature components
│                            and owns the state that belongs to that screen alone.
├─ features/<feature>/       One folder per product feature. Everything a feature
│                            owns lives inside it: its components, hooks, domain
│                            models, mock data and UI options.
├─ shared/                   Cross-feature building blocks, grouped by kind.
│  ├─ ui/                    Cross-feature presentational primitives only
│  │                         (BrandLockup, Eyebrow, TrendBadge, StatusDot,
│  │                         StatCard, Motion), the notifications API over Sonner
│  │                         (notifications.ts), and their shared prop/callback
│  │                         types. No domain or feature imports.
│  └─ animations/            Shared motion timings that any component may reuse.
│                            Holds no components and imports no features.
├─ components/
│  └─ ui/                    shadcn/ui primitives, generated by the shadcn CLI and
│                            owned by the app (chart — the Recharts wrappers — plus
│                            input). Presentational and domain-free, so any layer
│                            may import them.
├─ services/                 Outside-the-app boundary (the simulated /api/sync).
│                            Owns its request/response contracts.
└─ styles/                   Design tokens, the entry stylesheet and the shared
                             SURFACE recipe. CSS lives here, not in components.
```

Features today:

```
features/dashboard/
├─ components/    Presentational components for each dashboard region. The map is
│                 split across CampusMap (panel, controls, legend) → BinsMap
│                 (Google Map, markers, popup) → BinMarker / LocationPopup /
│                 MapNotice.
├─ hooks/         Feature hooks (useActiveSection — the dock's active destination,
│                 moved only by an explicit selection).
├─ types.ts       Domain models: NavItem, DashboardSummary, HardwareAlert,
│                 PointsByDay, WasteSortedPoint, BinTone and their tone unions.
├─ mockData.ts    Typed fixtures for the models above (MOCK_NOW is the snapshot's
│                 own clock, which the chart's period filter measures from).
├─ campusMapData.ts  The map's models (Bin, BinLocation), CAMPUS_CENTER and the
│                 mock bin locations, the marker-tone thresholds (FILL_THRESHOLDS
│                 with fillTone / locationTone / peakFill) and the view/zoom config.
├─ metricCards.tsx  Data descriptors for the overview metric cards (Metric[]),
│                 each carrying its own visual.
├─ options.ts     Static UI options (no domain data); WASTE_PERIODS is narrowed
│                 by isWastePeriod for the chart's `<select>`.
└─ wasteSeries.ts The waste chart's period filter: the series points a selected
                  period covers, measured from MOCK_NOW.

features/auth/
├─ components/    Reusable sign-in form pieces (LoginForm, TextField).
└─ types.ts       Sign-in form state models (LoginField, LoginErrors, LoginStatus).
```

`pages/` sits above the features and below the shell: it is the one place where
feature components meet, so a feature never imports a page.

The map's API key and optional Map ID come from Vite environment variables
(`import.meta.env.VITE_GOOGLE_MAPS_*`, typed in `src/vite-env.d.ts` and documented
in `FrontEnd/.env.example`). `BinsMap.tsx` is the only module that touches the
Google Maps library, just as `services/syncApi.ts` is the only module that
simulates the sync endpoint.

## Dependency direction

```
App ──► pages ──► features/* ──► shared/ui
          │            │   │
          │            │   └─────────► styles (SURFACE recipe)
          │            └─────────────► services (types/contracts)
          └──────────────────────────► shared/ui
```

Imports only ever point *down* this list, so there are no cycles:

- `shared/ui` and `styles` import nothing from pages, features or services.
- `components/ui` (the shadcn primitives) is presentational and domain-free, so
  it follows the same rule as `shared/ui`: any layer above it may import it.
- `services` imports nothing from the app.
- A feature may import `shared/ui`, `styles` and `services`, but not another
  feature's internals and never a page.
- A page may import any feature, `shared/ui`, `styles` and `services`; `App`
  imports only `pages/`, the shared notification API and the single Sonner
  `<Toaster />` it mounts for every screen.

Note `features/dashboard/mockData.ts` imports the `CachedSyncEvent` **type** from
`services/syncApi` — data fixtures are typed by the API contract, and the
dependency still points feature → service.

## Where new files belong

| Adding…                                          | Put it in…                                            |
| ------------------------------------------------ | ----------------------------------------------------- |
| A new screen/route                               | `pages/`, wired from `App`                            |
| A component that only one feature uses           | `features/<feature>/components/`                      |
| A hook, model, fixture or static option for one feature | `features/<feature>/`                          |
| A primitive reused by two or more features       | `shared/ui/`                                          |
| A shadcn/ui primitive (`npx shadcn add …`)       | `components/ui/`                                      |
| A shared animation timing or variant             | `shared/animations/`                                  |
| A new domain area (not just a screen)            | a new `features/<name>/` folder                       |
| A call to an external API                        | `services/`, with its request/response types beside it |
| A design token or global CSS rule                | `styles/` (tokens in `theme.css`)                     |

Prefer colocating over sharing: promote something to `shared/` only once a
second feature actually needs it.

## TypeScript conventions

- Strict mode, `verbatimModuleSyntax` and `noUnusedLocals`/`noUnusedParameters`
  are on (`tsconfig.json`); type-only imports use `import type`.
- Props, hook return values and service contracts have explicit interfaces.
  Domain types live with the feature that owns them; only genuinely shared types
  go in `shared/`.
- No `any`, no non-null assertions and no `@ts-ignore` — narrow with real checks
  (see `main.tsx` and `components/BinsMap.tsx`).
- External data is untrusted: a real sync implementation must validate the parsed
  response before returning it (see the note in `services/syncApi.ts`).
